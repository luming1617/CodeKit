# technical-doc 设计依据与现场数据（维护者文档）

> 本文件承接从 `SKILL.md` 与 `references/controller-contract.md` 移出的复盘叙事与实测数据。
> **运行时不注入**：主控与任何角色都不读取本文件，它不在派发清单里；修改流程规则时来这里查"为什么"，改完把规则本身同步回 SKILL.md / 契约 / check-standard / agents 与对应测试断言。

## 1. 读取预算与按节注入的由来

- 一份 5,000 行的 TDD 约 21 万 token，超过 20 万窗口：每一轮都整篇回读，就是某次运行把 54% 的 Refiner 时间花在"找那段在哪、现在写的是什么"上的原因。按节注入把翻页换成一次查表。
- 只改一处、漏掉引用它的那一处，是下一轮 Finding 的来源——所以 `locate --finding` 连带返回被编号引用的章节。
- 整篇可读始终是保留的退路：按节注入不是硬门禁，区间不足时允许扩大读取并要求声明。

## 2. 主控侧不整读原文的由来

- 某次运行主控整读 `product-doc.md` 3 次（58K 字符）、`context-pack` 2 次（35K 字符）。主控上下文里的这些东西没有导出机制，会一直占着窗口直到 run 结束——这才是主控比角色慢的原因，不是命令太多。
- 要核对 PRD 里的一句话，两条路：写成确认文件的待答条目，或让已经在读那份资料的角色在回报里引用原文位置；都不是自己翻页。

## 3. 严重度门停与增量终审的由来

- 某轮运行的 Finding 数是 Critic 26 条，随后每轮终审 12→7→5→3：`Blocker`/`High` 只在第 1 轮出现过，之后每轮的单条成本和第 1 轮完全一样，而每轮的 Reviewer 都把整篇重读一遍。
- 按这份现场数据回放门停规则，第 4、5 轮会被换成增量终审（实测推导范围约占整篇读取量的 52%），第 1～3 轮仍是全量——因为它们确实还在挖出阻断项。
- 5,046 行的文档实测下来，增量范围约 11.5 万 token，仍高于 0.5×窗口预算——但整篇读取（约 22 万 token）本来就超出 20 万窗口。所以增量轮 `over_budget` 不阻塞、也不靠拆派发解决（一轮只允许一个全新 Reviewer 实例）。
- **P1-1 决策（已拍板）**：门停从“连续两轮干净”放宽为“上一轮干净即增量”（`SEVERITY_STOP_STREAK` 2→1），用两条新增的机械刹车换中部放宽：增量轮不得连续（上一轮是增量则本轮强制全量）、交付轮必须全量（增量结论不得进 DELIVERY，须经落地回退补一轮全量，即使没有未处置 Finding 也放行回退）。取舍：单轮干净可能是 Reviewer 漏报的噪声，尾部强制全量是第二道网；最坏后果是多花一轮，不是漏检交付。被拒的替代方案：只放宽 streak 不加交付轮全量（失去尾部兜底）；轮次上限 5→4（挤压落地回退预算，未采纳）。

## 4. 规模判定与绿地裁剪的由来

- 模板的 `方案裁剪规则` 早就写了 S/M/L 三行，但没人判定归属，于是绿地原型也按 L 填满可观测设计与部署拓扑章节，每轮再被整篇读回一遍。
- 某次运行在"现有实现与可复用模式"检索上花 36 分钟去找不存在的代码——`greenfield` 判定后 Context Loader 明确跳过该检索，缺口照旧写"未发现证据"。
- `工程与模块` 一章的两条互斥分支从来没人判定走哪条，于是同一章既能被填成占位表格、也能被推给"待初始化"；现在分支由 `greenfield` 实测选定。
- 枚举源码时跳过根下 `doc/`、`docs/`：PRD/TDD/示例工程片段就住在这里，把它们当代码会让一个还没定工程结构的仓库被判成"既有实现"。
- "无 MQ、单进程、附替代方案对比"的一章实测合法：条件必填章节的退路是"不涉及 + 原因"，给得出理由就合法，只有一句"不涉及"才阻塞。

## 5. 命令手册与回读禁令的由来

- 上一版 SKILL.md 的命令表把契约手册的拒绝理由抄了一遍，长到占整页 17%（约 5,184 / 30,000 字符），而主控真正会撞上的那几条在手册里逐条都有；其中一行还在单元格里带了裸 `|`，撕裂了表格渲染。现在命令表只留用途与该步需要主控拿的主意（11 行、每行第二列 ≤260 字符，由测试锁定），拒绝语义只在 `controller-contract.md` 说一次。
- 某次运行主控回读控制器源码凑参数发生了 14 次，每次都是同一个问题（"这一步还缺什么"），而 `show --next` 就是为这个问题准备的答复。控制器是五千余行的实现，run 中途回读它是最贵的答疑方式。

## 6. 镜像检测前移与体积软检查的由来

- 手抄台账只在交付时被拒，于是主控每场都人工 strip 两次；某份参考运行里一份手抄镜像约 47,000 字符，贡献了 53 条 Finding 里的 14 条，全是关于镜像本身的。现在镜像检测前移到 `write-artifact` / `record-fix` / `record-fixes` 三个入账时刻。
- 镜像判据在表头不在字样：模板自带的 `评审人意见` 表带"处理结论"列但没有引用 Finding ID 的列，按字样判定会误伤人工要填的表——两半表头同时命中才是镜像。
- 正文增长原先完全没有测量，每轮 +15% 的读取量不出现在任何记录里。`document-growth` 软检查（8% 阈值）让每轮灌水变成一个被记录下来的代价：角色每多读 15% 就是每一轮多花 15% 的时间。它永不阻塞，唯一的牙齿是交付报告强制照抄。
- 体积参照在 `draft` 落盘时冻结（`UPDATE` 取被重写的那一版），任何一轮均不得事后改写参照。
- **P1-3 决策（已拍板）**：软检查记账不够——每轮 +15% 的灌水在单轮 diff 里看不见，累积到交付时读取量已翻倍。新增硬检查 `document-growth-hard`：无主增长（本轮无 `Blocker`/`High` 买单）超过 `GROWTH_BLOCK_PERCENT`（25%）直接 `BLOCKED`，与 8% 软警告共用同一套 `_growth_facts` 推导，不会互相矛盾。阈值 25% 是先拍板后回放校准的首版值。唯一出路是 Reviewer 裁定豁免（A+B 组合）：`waive-growth` 只在 `DELIVERY`、必须引用最新终审轮的 REVIEWER Finding 并给理由，豁免进台账与交付报告强制照抄；回退开新轮自动作废旧豁免（裁定针对那一轮读过的文档）。B 信号：`show` 的 `large_sections` 点名超过 `LARGE_SECTION_LINES`（300）行的章节，Refiner 优先重写该节而非追加。取舍：硬阈值可能误伤“必要但无人买单”的增长（例如 Reviewer 要求展开的完整契约），由豁免通道兜住；风险（主控自裁豁免）由“必须锚定最新轮 REVIEWER Finding”的机械校验兜住——Critic 的、往轮的、不存在的 Finding 都拒。被拒的替代方案：只加软警告不加硬门（灌水无牙齿，未采纳）；豁免由主控自述理由（失去独立裁定锚点，未采纳）。

## 7. 轮次与落地回退的由来
- `REVIEW --to REFINER` 曾经要求 Finding 必须是本轮 Reviewer 报的，结果是带着旧 Finding 进终审的 run 三面碰壁：`--to DELIVERY` 拒未闭环、`--to REFINER` 说不是本轮报的、`record-fix` 说不在 `REFINER` 阶段。现在判据是台账上还有没有未登记处置的 Finding，往轮遗留的同样算。
- 终审之后才收口的人工决定原先只有一条出路（重放流水线）；`DELIVERY --to REFINER` 落地回退把"必须改正文才能收口"的门禁失败（scale-chapters 太薄、project-structure-branch 走错分支等）也纳入同一条合法通道。门守卫的是代价（一整轮终审预算）而不是理由。
- 降级曾经是全 skill 唯一一处"退出码 0 但结论不成立"的通道；现在状态推导只有一条：`failures` 非空即 `BLOCKED`，`PARTIAL_DEGRADED` 只顶替"无降级 + 无失败"的 PASS 位置。
- 某场第 2、3 轮终审报出的 12 与 7 条里没有一条 `Blocker`/`High`，两轮约 100 分钟模型时间花在"给不需要改正文的 Finding 改正文"上——这是通过性结论后非阻断 Finding 默认就地收口的依据。
- 同一份文档一轮串行改 15 条 Finding 时，模型时间几乎全花在“读同一份文档的下一段”上；按章节聚簇并行派发多个 Refiner 实例后，实测从 20+ 分钟降到 7 分钟。
- **P1-2 决策（已拍板）**：机械缺陷不再一律烧整轮。通道①：`apply-mechanical-patch` 允许主控在 DELIVERY 用只删行的校验 diff 直修两类语义中性缺陷（手抄镜像表行、已 APPLIED 条目残留的整行 marker），不消耗轮次；边界由代码圈定：正文必须仍与终审快照逐字一致、每条被删行必须命中所声明检查的谓词、补丁进台账强制照抄。首版白名单只开这两项，运行一场后再评估扩展。通道②：落地回退后的补审轮默认增量（上一轮全量且通过、范围从修复 diff 推导），其增量结论可直接交付——这是“交付轮必须全量”的唯一例外，由 gate 覆盖证明兜底。取舍：通道①是“主控不得改正文”底线的显式例外，风险（误删有效内容）由只删不增 + 谓词逐行校验 + 台账可见性兜住；通道②的风险（修复的跨章节影响漏审）由引用展开与覆盖证明兜住。被拒的替代方案：白名单首版即开四项（嵌套围栏、占位符涉及内容替换，语义中性无法机械证明，未采纳）。

## 8. 确认循环的由来

- `CONFIRM_NEEDED` 提前收口若登记 `ABORTED`，等于宣布已落盘的半份草稿不存在，主控会被推回去重做已完成的一半——所以它按 `COMPLETED` 登记。
- 一条非阻断的"建议尽快定"把整轮停在桌上，代价是一整轮终审——所以阻断判据是唯一的暂停理由，由产出角色按判断式裁决。
- marker 格式不写进模板：粘进模板会逐字到达每份草稿，而未登记的 marker 正是 `markers-match-confirmations` 拦的东西。
