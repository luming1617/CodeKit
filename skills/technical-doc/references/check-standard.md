# 技术方案质量判据（Quality Standards）

> `technical-doc` 的 Critic、Refiner 与独立 Reviewer 在审查 TDD 时按本文档判定质量。
> 发布方案与代码审查的判据分别由 `release-doc`、`code-review` 自己的 references 承载，不在本文件范围内。

## 判定分工

| 类别 | 由谁判定 |
|------|----------|
| 章节齐整、占位符、围栏闭合、Finding 闭环、轮次上限、终审快照一致 | `scripts/tech_doc_controller.py gate`（确定性，退出码即结论） |
| 设计是否成立、风险是否真实、权衡是否充分 | Critic / Reviewer（本文件的判据） |

模型不要重复判定控制器已经机械判定的项目，把注意力留给需要判断力的部分。

## 总体原则

1. **Concise is Key**：只写技术决策需要的内容，不复制 PRD；背景与现状不构成独立篇幅目标。
2. **方案可执行**：描述到代码/配置/接口级别，不能停留在概念层。
3. **权衡显式**：有多方案时比较优劣并给出推荐与被放弃项。
4. **风险前置**：识别风险与外部依赖，标注阻断项。
5. **渐进披露**：先高层架构，再深入细节；详细设计应是文档的主体内容。

## 结构完整性（与 `gate` 锚点一一对应）

- [ ] 文档信息与变更记录（版本/日期/变更类型齐备）
- [ ] 需求到设计追踪：每个 PRD 功能点与非功能需求都有落点
- [ ] 关键技术决策记录（ADR）：编号、背景、决策、候选方案对比、后果、证据或假设
- [ ] 风险登记与工作量评估：风险不少于 2 条，工作量按模块拆分并标注依赖
- [ ] 审查闭环记录：Finding 处置映射、`review_round`、最终评审状态
- [ ] 需求变更时保留上一版 TDD 的历史版本索引（归档文件路径，不内嵌正文）

## 内容质量

- [ ] 每个改造点有“现有方式 → 新方式”对比（含代码或契约片段）
- [ ] 数据模型有完整 DDL（`CREATE TABLE` 含字段、索引、注释）
- [ ] 新增接口有完整请求/响应 JSON、错误码、鉴权、幂等和兼容说明
- [ ] 性能要求有量化指标（P95/P99 响应时间、QPS、数据量、恢复时间目标）
- [ ] 背景与现状不复制 PRD，详细设计构成文档主体
- [ ] 无占位符：唯一允许的未知表达是 `[需人工确认: xxx]`，且写明影响哪项决策

## 设计合理性

- [ ] 服务边界清晰（本服务做什么、不做什么、外部依赖如何集成）
- [ ] 设计决策有理由说明（Why this approach），且能追溯到证据或显式假设
- [ ] 假设显式列出
- [ ] 未引入不必要的复杂性（新框架/中间件/抽象层需有充分理由）
- [ ] 改动范围聚焦在需求内，无“顺便”重构

## 可操作性

- [ ] 兼容性与灰度/回滚步骤明确（字段、默认值、版本或降级语义，不能只写“兼容”）
- [ ] 外部依赖已标注（系统名称/对接方式/责任方）
- [ ] 监控与告警设计到可落地级别（指标名、阈值、处置入口），规模小的方案可裁剪到基础项并说明理由
- [ ] 可验证项已验证；无法验证的（编译、测试、Schema、契约）记录原因，不得声称已验证
