# 技术方案质量判据（Quality Standards）

> `technical-doc` 的 Critic、Refiner 与独立 Reviewer 在审查 TDD 时按本文档判定质量。
> 发布方案与代码审查的判据分别由 `release-doc`、`code-review` 自己的 references 承载，不在本文件范围内。

## 判定分工

| 类别 | 由谁判定 |
|------|----------|
| 章节齐整、占位符、围栏闭合、Finding 闭环、轮次上限、终审快照一致且覆盖当前开放轮次、增量终审是否覆盖自最后一次全量终审以来变过的每一节（`incremental-review-covers-changes`）、按规模判定的章节实质内容（`scale-chapters`）、“审查闭环记录”章节生成台账与 `state.json` 逐字一致 | `scripts/tech_doc_controller.py gate`（确定性，退出码即结论） |
| 设计是否成立、风险是否真实、权衡是否充分 | Critic / Reviewer（本文件的判据） |

模型不要重复判定控制器已经机械判定的项目，把注意力留给需要判断力的部分。

## 审查范围与规模的判据

- **全量轮**：读完整篇，按本文档全部判据审查。前两轮、以及任何报出 `Blocker`/`High` 或留下未闭环 `must_fix` 的轮次之后，都是全量轮。
- **增量轮**：只在连续两轮既无 `Blocker`/`High` 又无未闭环 `must_fix` 之后出现，范围由控制器给出（变过的章节 + 上一轮 Finding 所在章节）。判据不变，但结论只对这些章节负责：范围外的内容沿用上一轮结论，发现范围外的问题照常登记并说明它不在本轮范围内，**不得把增量结论写成全量结论**。被裁掉的读取量由 `gate` 的覆盖证明兜底，不靠审查者自我约束。
- **规模**：任何规模下规模相关章节都要在位。`M`/`L` 级的可观测设计、`L` 级的部署拓扑必须有实质设计，收缩即阻塞；被信号点名的 `条件必填` 章节保留 `不涉及 + 原因` 的退路，`S` 级则可观测设计收缩到基础项、部署拓扑不在要求之列。审查者的判断留给“这一节写的是不是真能落地”（指标名、阈值、处置入口）以及“那个 `不涉及` 的理由站不站得住”，`不涉及` 是否给足形式由 `gate` 按 `state.json` 的机械判定拦。规模判定本身是探针测量结果，不因文档写得长而改变。

## 总体原则

1. **Concise is Key**：只写技术决策需要的内容，不复制 PRD；背景与现状不构成独立篇幅目标。
2. **方案可执行**：描述到代码/配置/接口级别，不能停留在概念层。
3. **权衡显式**：有多方案时比较优劣并给出推荐与被放弃项。
4. **风险前置**：识别风险与外部依赖，标注阻断项。
5. **渐进披露**：先高层架构，再深入细节；详细设计应是文档的主体内容。

## 章节标题与必填判定

- 模板标题不带数字序号，章节是否齐整一律按**标题名称**对齐判定；TDD 自身的编号由 Architect 落盘时生成，不得因编号与模板标题对不上而报 Finding，也不得要求模板携带编号。
- 标题中未标注“必填 / 条件必填 / M-L 级必填”等说明的章节，默认按**必填项**处理：缺失、空置或以占位符交差都是 Finding，删除该章节同理。
- 标题只写级别要求的章节（如 `非功能设计（M/L级必填）`、`部署拓扑（L 必填）`）在该级别为必填，低于该级别不要求实质内容。
- 标题中标注“条件必填”的章节（接口与契约设计、数据库设计、缓存设计、消息设计、定时任务设计、环境配置设计，及各章节内标注条件必填的小节），按本需求实际情况判定：需求确实涉及该类别即为必填，必须给出实质设计；确实不涉及的无需填写设计内容，但按模板保留章节并写明“不涉及”及原因——“不涉及”的形式是否给足由 `gate` 机械判定（见“审查范围与规模的判据”），理由站不站得住由审查者判断。

## 结构完整性（与 `gate` 锚点一一对应）

- [ ] 文档信息与变更记录（版本/日期/变更类型齐备）
- [ ] 影响范围：每个 PRD 功能点与非功能需求都有需求到设计的落点
- [ ] 关键技术决策记录（ADR）：编号、背景、决策、候选方案对比、后果、证据或假设
- [ ] 里程碑规划：风险登记不少于 2 条，工作量按模块拆分并标注依赖，各期可独立交付验收
- [ ] 待人工确认项：编号台账收敛全部需要人裁决的开放项，出处指向真实章节
- [ ] 审查闭环记录：本章的两个台账由 `render-ledger` 生成，只判断处置理由是否成立，不逐字复核表格（机械一致性由 `gate` 负责）
- [ ] 变更历史：需求变更时保留上一版 TDD 的历史版本索引（归档文件路径，不内嵌正文）
- [ ] 依赖设计：包依赖和接口依赖完整

## 内容质量

- [ ] 每个改造点有“现有方式 → 新方式”对比（含代码或契约片段）
- [ ] 数据模型有完整 DDL（`CREATE TABLE` 含字段、索引、注释）
- [ ] 新增接口有完整请求/响应 JSON、错误码、鉴权、幂等和兼容说明
- [ ] 性能要求有量化指标（P95/P99 响应时间、QPS、数据量、恢复时间目标）
- [ ] 背景与现状不复制 PRD，详细设计构成文档主体
- [ ] 无占位符：唯一允许的未知表达是 `[需人工确认: xxx]`，且写明影响哪项决策

## 设计合理性

- [ ] 服务边界清晰（本服务做什么、不做什么、外部依赖如何集成）
- [ ] 设计决策有理由说明（Why this approach），且能追溯到证据或显式假设
- [ ] 假设显式列出
- [ ] 未引入不必要的复杂性（新框架/中间件/抽象层需有充分理由）
- [ ] 改动范围聚焦在需求内，无“顺便”重构
