# 技术方案质量判据（Quality Standards）

> `technical-doc` 的 Critic、Refiner 与独立 Reviewer 在审查 TDD 时按本文档判定质量。
> 发布方案与代码审查的判据分别由 `release-doc`、`code-review` 自己的 references 承载，不在本文件范围内。

## 判定分工

| 类别 | 由谁判定 |
|------|----------|
| 章节齐整、占位符、围栏闭合、Finding 闭环、轮次上限、终审快照一致且覆盖当前开放轮次、增量终审是否覆盖自最后一次全量终审以来变过的每一节（`incremental-review-covers-changes`）、按规模判定的章节实质内容（`scale-chapters`）、`工程与模块` 是否走了探针选定的那条分支（`project-structure-branch`）、“审查闭环记录”章节生成台账与 `state.json` 逐字一致、正文 需人工确认 marker 与确认条目是否双向对得上（`markers-match-confirmations`）、确认文件是否持久并与 `state.json` 逐条一致（`confirmations-file-persisted`） | `scripts/tech_doc_controller.py gate`（确定性，退出码即结论） |
| 设计是否成立、风险是否真实、权衡是否充分 | Critic / Reviewer（本文件的判据） |

模型不要重复判定控制器已经机械判定的项目，把注意力留给需要判断力的部分。

## 审查范围与规模的判据

- **全量轮**：读完整篇，按本文档全部判据审查。第 1 轮、任何报出 `Blocker`/`High` 或留下未闭环 `must_fix` 的轮次之后、以及增量轮的下一轮，都是全量轮；交付轮必须全量。
- **增量轮**：只在上一轮既无 `Blocker`/`High` 又无未闭环 `must_fix`、且上一轮不是增量轮之后出现（**增量轮不得连续**），范围由控制器给出（变过的章节 + 上一轮 Finding 所在章节）。判据不变，但结论只对这些章节负责：范围外的内容沿用上一轮结论，发现范围外的问题照常登记并说明它不在本轮范围内，**不得把增量结论写成全量结论**。被裁掉的读取量由 `gate` 的覆盖证明兜底，不靠审查者自我约束；**交付轮必须全量**——最后一次终审是增量的，交付前必须补一轮全量终审，增量结论不能直接支撑交付；唯一例外是落地回退后的补审轮（上一轮全量且通过、范围由修复 diff 推导，补审默认增量），其增量结论可直接交付，覆盖证明照旧生效。
- **规模**：任何规模下规模相关章节都要在位。`M`/`L` 级的可观测设计、`L` 级的部署拓扑必须有实质设计，收缩即阻塞；被信号点名的 `条件必填` 章节保留 `不涉及 + 原因` 的退路，`S` 级则可观测设计收缩到基础项、部署拓扑不在要求之列。审查者的判断留给“这一节写的是不是真能落地”（指标名、阈值、处置入口）以及“那个 `不涉及` 的理由站不站得住”，`不涉及` 是否给足形式由 `gate` 按 `state.json` 的机械判定拦。规模判定本身是探针测量结果，不因文档写得长而改变。
- **工程与模块分支**：空仓库要先初始化工程结构，已有代码的仓库要列出改动模块，走哪条由 `finalize-inputs` 的 `greenfield` 实测选定，形式是否齐备由 `gate` 的 `project-structure-branch` 机械判定。审查者判的是分支与内容是否站得住：分类与你在上下文包里看到的现状矛盾（判成绿地却检索到在跑的服务，或反之）按事实登记 Finding 并给出证据路径；结构方案照抄模板示例、模块表只有一行“见代码”这类空转，同样按 Finding，不因“门禁已经放行”而免检。

## 固有缺口分流

已经被登记为开放问题的缺口不是设计缺失。Critic 定级时，**同时满足**以下三个条件的缺口记 `Medium` 非阻塞，并在 `@@FIND` 行附 `gap_ref=` 引用登记位置：

1. 缺口已在冻结 PRD 中登记为开放项（Q/待补充/明确未定项），或已在 `confirmation-log.md` 有 OPEN 条目；
2. TDD 对应位置已写 `[需人工确认: xxx]` marker，并说明了它影响哪项决策；
3. Finding 证据逐字引用登记位置（`gap_ref=CONF-<NNN>` 或 `gap_ref=PRD:<章节>`；控制器校验格式与 CONF 条目存在性）。

缺任一条件照常按影响定级：未登记的缺口、该挂 marker 却写成肯定结论的位置，是真实缺陷，不在分流之列。`gap_ref` 只能附在非阻塞 Finding 上（附在 `must_fix` 上会被控制器拒绝）——它是引用，不是降级开关。分流不改变闭环要求：该 Finding 仍需一条处置，marker 与条目的双向对账照旧由 `gate` 判定。

Reviewer 复核分流合法性：带 `gap_ref` 的 Medium 要核对引用位置是否真实存在、marker 是否真的在正文——引用不存在或 marker 缺失的是降级逃逸，按原严重度重报；“marker 是否真的需要人拍板”仍按“人工决定与 marker”一节判定。

## 总体原则

1. **Concise is Key**：只写技术决策需要的内容，不复制 PRD；背景与现状不构成独立篇幅目标。
2. **方案可执行**：描述到代码/配置/接口级别，不能停留在概念层。
3. **权衡显式**：有多方案时比较优劣并给出推荐与被放弃项。
4. **风险前置**：识别风险与外部依赖，标注阻断项。
5. **渐进披露**：先高层架构，再深入细节；详细设计应是文档的主体内容。

## 章节标题与必填判定

- 模板标题不带数字序号，章节是否齐整一律按**标题名称**对齐判定；TDD 自身的编号由 Architect 落盘时生成，不得因编号与模板标题对不上而报 Finding，也不得要求模板携带编号。
- 标题中未标注“必填 / 条件必填 / M-L 级必填”等说明的章节，默认按**必填项**处理：缺失、空置或以占位符交差都是 Finding，删除该章节同理。
- 标题只写级别要求的章节（如 `非功能设计（M/L级必填）`、`部署拓扑（L 必填）`）在该级别为必填，低于该级别不要求实质内容。
- 标题中标注“条件必填”的章节（接口与契约设计、数据库设计、缓存设计、消息设计、定时任务设计、环境配置设计，及各章节内标注条件必填的小节），按本需求实际情况判定：需求确实涉及该类别即为必填，必须给出实质设计；确实不涉及的无需填写设计内容，但按模板保留章节并写明“不涉及”及原因——“不涉及”的形式是否给足由 `gate` 机械判定（见“审查范围与规模的判据”），理由站不站得住由审查者判断。

## 结构完整性（与 `gate` 锚点一一对应）

- [ ] 文档信息与变更记录（版本/日期/变更类型齐备）
- [ ] 影响范围：每个 PRD 功能点与非功能需求都有需求到设计的落点
- [ ] 关键技术决策记录（ADR）：编号、背景、决策、候选方案对比、后果、证据或假设
- [ ] 里程碑规划：风险登记不少于 2 条，工作量按模块拆分并标注依赖，各期可独立交付验收
- [ ] 待人工确认项：编号台账收敛全部需要人裁决的开放项，出处指向真实章节
- [ ] 审查闭环记录：本章的两个台账由 `render-ledger` 生成，只判断处置理由是否成立，不逐字复核表格（机械一致性由 `gate` 负责）
- [ ] 变更历史：需求变更时保留上一版 TDD 的历史版本索引（归档文件路径，不内嵌正文）
- [ ] 依赖设计：包依赖和接口依赖完整

## 内容质量

- [ ] 每个改造点有“现有方式 → 新方式”对比（含代码或契约片段）
- [ ] 数据模型有完整 DDL（`CREATE TABLE` 含字段、索引、注释）
- [ ] 新增接口有完整请求/响应 JSON、错误码、鉴权、幂等和兼容说明
- [ ] 性能要求有量化指标（P95/P99 响应时间、QPS、数据量、恢复时间目标）
- [ ] 背景与现状不复制 PRD，详细设计构成文档主体
- [ ] 无可压缩冗余：同一结论不在多节重复展开，修复 Finding 优先重写该节而非追加段落。正文相对冻结参照的无主增长由 `gate` 度量：`document-growth`（8% 软警告）与 `document-growth-hard`（25% 硬阻塞，唯一出路是 Reviewer 裁定豁免）；超过 300 行的超大章节由 `show` 的 `large_sections` 点名，是优先压缩对象
- [ ] 无占位符：唯一允许的未知表达是 `[需人工确认: xxx]`，且写明影响哪项决策（该 marker 必须有确认文件条目对应，由 `gate` 机械判定，不必重复核对）；槽位有两类，判定口径不同——**槽位词**（`待定`、`待补充`、`后续补充`）和**任何残留的方括号填写标记**（`【…】`，逐字清单曾放过 `【填写/不涉及】`、`【通过/不通过/不涉及】`，所以门禁按“还剩下方括号”而非枚举括号里的字）出现在任何位置都算未填写；例外是 `【新增】/【修改】/【删除】` 三个变更标记，那是内容不是槽位。但 DDL、接口示例与行内代码里的同形取值（状态枚举 `todo`、日期格式）是数据，不是占位符，不要为此开 Finding

## 设计合理性

- [ ] 服务边界清晰（本服务做什么、不做什么、外部依赖如何集成）
- [ ] 设计决策有理由说明（Why this approach），且能追溯到证据或显式假设
- [ ] 假设显式列出
- [ ] 未引入不必要的复杂性（新框架/中间件/抽象层需有充分理由）
- [ ] 改动范围聚焦在需求内，无“顺便”重构

## 人工决定与 marker

机械面（marker 与条目是否双向对得上、确认文件与 `state.json` 是否逐条一致、收口决定有没有登记落点）由 `gate` 与 `start-stage` 判定，不重复核对。剩下三件事要判断力：

- [ ] **落地是否忠实**：`state.json` 里已登记落点（`应用:` 非空）的决定，正文对应章节是否真的按该决定改写，且没在不相干的章节留下旧方案——落了 A 却在依赖 A 的那一节继续按 B 设计，是按影响定级的真实缺陷，不是笔误。`[已人工确认: … → …]` 的结论部分与台账里的 `决定:` 不一致同理。
- [ ] **挂账是否诚实**：条目已裁定但本 run 没把它写进正文（终审之后才收口、落地回退的那一轮终审没有付、或已到达轮次上限）时，正文保留原 marker、台账标注“待落地”是允许的最终态。此时要判的是它是否**真的**可以不落地：按另一种答案需要改写核心接口、数据模型、兼容或发布顺序的，就应当是 `阻断: true` 并走 `REQUEST_CHANGES`，而不是挂账放行——挂账条目被写成设计已定，是 Finding；反过来，一个改动小到自己都说不清为什么要为它再烧一轮终审的条目被留在正文里问，也是 Finding。
- [ ] **marker 是否真的需要人拍板**：`[需人工确认: xxx]` 只承载“证据不足、模型无法裁决”的事实或选择。可以自行查证却写成 marker 是躲活；反过来，本该挂 marker 的未证事实被写成肯定结论，`gate` 看不见，只有审查者看得见。
- [ ] **问题是否被抹掉而不是被回答**：台账里仍有一条未收口条目，正文对应位置却已找不到它的 marker，且那一节被改写得像是已经有了结论——这是 `gate` 判不了的方向（marker 消失永远合法，孤儿条目才由台账兜住），只能由审查者按“未决问题被伪装成已决”定级；如果该未知确实因设计变化不再成立，正当写法是在处置理由里说明它不再成立。
