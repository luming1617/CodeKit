# 修复方案选择与审批

## 1. 最佳修复的含义

最佳方案不是机械地选择“改动行数最少”，而是在正确责任层修复根因，并在以下约束下取得最优平衡：

- 正确恢复 PRD 业务语义和 TDD 技术不变量；
- 修改文件和影响路径最少；
- 不改变无关业务、公开契约、数据语义和运行默认值；
- 兼容旧客户端、旧数据、旧消息和混合版本部署；
- 修复成本、验证成本和发布风险合理；
- 能用自动化回归测试证明，并能按 RPD 安全发布和回滚；
- 不依赖隐藏配置、永久人工操作或吞错来掩盖症状。

## 2. 方案候选

有多个可行方案时，用同一矩阵比较；只有一个合理方案时，说明其他常见做法为什么不适用。

| 维度 | 评价问题 |
|---|---|
| 根因覆盖 | 是否消除根因，而不是只拦截某个症状？ |
| 业务保持 | 哪些行为会改变，哪些明确保持不变？ |
| 影响范围 | 涉及哪些文件、模块、调用者、数据和发布单元？ |
| 兼容性 | 新旧 API、数据、消息、配置和实例能否共存？ |
| 风险 | 是否引入并发、事务、安全、性能或运维风险？ |
| 成本 | 实现、测试、Migration、发布和长期维护成本如何？ |
| 可验证性 | 能否构造修复前失败、修复后通过的回归测试？ |
| 可回滚性 | 代码、配置和数据是否都能恢复？ |

## 3. 影响面证明

修复方案必须检查：

- 被修改符号的调用者、实现、覆盖、序列化和测试；
- API、DTO、枚举、错误码和协议消费者；
- 表结构、索引、约束、历史数据、事务和 Migration；
- 消息生产者/消费者、缓存 Key、配置项、Feature Flag 和 Job；
- 鉴权、租户、隐私、审计、日志、指标和告警；
- 性能关键路径、资源池、容量和 RPD；
- 构建、打包、部署、灰度、回滚和数据修复。

明确列出 `behavior_to_preserve` 和 `forbidden_changes`，让“不会影响其他业务”成为可检查的约束，而不是承诺句。

## 4. 修复提案最低内容

提案至少包含：

1. `proposal_id`、版本和绑定快照；
2. 问题判定及期望/实际行为；
3. 症状、触发条件、根因、促成因素和证据链；
4. 被排除的替代假设；
5. 推荐方案、备选方案和选择理由；
6. 精确允许修改文件与明确禁止项；
7. 逐文件/符号的计划变化；
8. 需要保持的业务不变量；
9. 影响面、兼容性、风险和缓解措施；
10. 回归、集成、契约、发布和人工验证计划；
11. 成本估算和回滚策略；
12. 可复制的人工审批口令。

## 5. 审批语义

推荐审批口令：

```text
批准执行 <proposal_id> v<proposal_version>，按当前绑定快照和允许修改文件实施。
```

以下内容不构成审批：

- “看起来可以”“继续分析”“你再确认一下”；
- 只批准某个观点但未批准实施；
- 批准了旧版本方案；
- 用户要求修改方案或提出尚未回答的问题；
- 代码快照发生无法归因的变化；
- 方案需要新增文件、Migration、依赖或外部变更。

批准后也只授权方案列出的仓库修改；commit、push、部署、真实数据修复、真实 Migration、外部消息和生产操作仍需要用户明确授权。

## 6. 不同问题判定的输出

- `CONFIRMED_BUG`：输出完整问题原因和修复方案，状态为 `WAITING_APPROVAL`，然后停止。
- `NOT_A_BUG`：输出证据化原因和正确使用/配置/数据处理建议；不创建可执行修复合同。
- `INSUFFICIENT_EVIDENCE`：输出当前假设、缺失证据和最小采集方案；不提交猜测性修复。
