# 后端问题调查 Playbook

## 1. 先理解业务，再解释代码

把 PRD 中的业务目标转换为小型可执行模型：谁在什么权限和前置状态下，对哪个实体执行什么动作，允许产生哪些状态和副作用，哪些不变量永远不能破坏。

至少回答：

- 参与者、租户和权限边界是什么？
- 正常、边界、异常、重试和并发路径分别是什么？
- 哪些状态转换合法，哪些必须拒绝？
- 数据一致性、时效、顺序、唯一性、金额精度或库存等不变量是什么？
- TDD 如何实现这些约束？RPD 假设怎样的部署、配置和混合版本状态？
- 当前症状违反了哪条明确约束？

文档不能解释真实行为时，记录 `Unclear` 或冲突；不要自行创造业务规则。

## 2. 把症状变成可检验断言

使用结构：

```text
Given 业务状态、配置、数据版本和依赖状态
When 请求、事件、任务或并发动作发生
Then 权威规格要求的结果
But 实际观察到的结果
```

分离：

- **症状**：用户或系统看到什么；
- **触发条件**：什么输入和状态使它出现；
- **根本原因**：哪个错误决策或状态破坏了不变量；
- **促成因素**：使故障更容易发生或更难发现的条件。

## 3. 证据采集顺序

优先选择成本低、区分度高、可重复且无副作用的证据：

1. 已有失败测试或最小只读复现；
2. 精确日志、Trace、指标、请求响应和错误码；
3. 代码控制流、数据流、Schema、配置和依赖版本；
4. 安全脱敏的数据形态或状态快照；
5. 受控测试环境中的实验；
6. 生产变更或真实外部副作用永远不作为默认诊断手段。

记录证据的时间、环境、版本和适用边界。时间不一致的日志、不同版本的代码和已变化的配置不能拼接成虚假因果链。

## 4. 根因定位路径

沿以下链路双向追踪：

```text
入口/事件
→ 参数解析与校验
→ 身份、权限与租户上下文
→ 业务规则与状态机
→ 事务、数据库、缓存和消息
→ 下游调用、异步任务或定时任务
→ 返回值、事件、副作用和可观测信号
```

对每个关键分支记录：输入值、Guard、状态变化、异常处理、重试行为、提交点和输出。搜索调用者与消费者，不能只看报错行。

## 5. 互联网后端专项检查

本节是按需展开的清单，不是每次全读的清单。先用步骤 01–04 的症状确定改动落在哪条链路上，**只展开命中的小节**；与本次路径无关的小节直接记 `不适用`，不要为凑齐清单去读代码。文档定位一律走 `RUN_DIR/doc-map.md` 的标题区间。

### API 与兼容性

检查参数缺省、Optional/Null、枚举扩展、序列化、错误映射、分页、时区、版本、旧客户端、混合版本实例和下游契约。

### 权限、安全与隐私

检查认证、对象级/功能级授权、租户隔离、输入注入、SSRF、反序列化、密钥、签名、防重放、PII 泄露、审计和 fail-open。

### 数据、事务与并发

检查事务边界、隔离级别、锁顺序、乐观锁、丢失更新、唯一约束、金额精度、幂等、DB/消息/缓存原子性、补偿和对账。

### RPC 与依赖

检查超时层级、Deadline 传播、重试放大、退避抖动、连接池、熔断、限流、降级数据时效、错误契约和不确定提交结果。

### MQ、事件与 CDC

检查生产事务、分区键、顺序范围、重复/乱序消费、幂等、Schema 演进、重试、DLQ、积压、回放和 Outbox/Inbox。

### 缓存

检查 Key 和租户隔离、TTL、失效顺序、穿透、击穿、雪崩、负缓存、旧值、序列化升级、容量和缓存不可用行为。

### 异步、Job 与时间

检查重复调度、并发执行、Misfire、取消、任务丢失、恢复、线程池/队列边界、时区、夏令时、时钟偏移、Leader 和 Fencing。

### 配置与发布

检查默认值、缺失值、动态刷新、Feature Flag、旧实例含义、环境差异、灰度、回滚、Schema 兼容、数据修复和 RPD 停止条件。

### 性能与容量

检查 N+1、查询计划、复杂度、无界集合、对象分配、锁竞争、连接池、队列、Fan-out、批处理、背压、峰值负载和容量阈值。

## 6. 反证与 NOT_A_BUG 标准

Challenger 至少检查：

- PRD/TDD 是否明确规定当前行为；
- 调用方是否违反输入契约或权限约束；
- 环境、配置、数据修复、上游或下游是否是责任边界；
- 日志是否来自另一版本、实例、租户或请求；
- 复现步骤是否缺少必要状态；
- 已有 Guard、事务或框架语义是否使候选路径不可达；
- 观察到的是允许的最终一致性、降级或灰度行为，而不是错误。

证明“不是 Bug”必须同时说明预期行为的权威来源、实际行为证据、两者为何一致，以及用户症状的真实解释。不能只说“无法复现”。

## 7. 根因完成条件

根因只有满足以下条件才算完成：

1. 能从输入/状态完整推导到症状；
2. 指向精确文件、符号、配置、Schema 或责任边界；
3. 说明违反的业务或技术不变量；
4. 有 E2/E3 证据；
5. 主要替代假设已被证据拒绝；
6. 修复该原因后，原触发路径将被回归测试覆盖；
7. 解释影响范围及为什么其他业务路径不应改变。
