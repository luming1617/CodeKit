# 后端服务发布方案模板

> 适用范围：普通业务迭代、低风险配置变更、非核心后台功能、影响范围可控且具备标准回滚能力（P2/P3）的需求发布。
>
>
> **强制规则：**
> 1. 所有适用于本次发布的检查项必须校验通过；
> 2. 不适用的检查项必须明确标记为“**不涉及**”并说明原因；
> 3. 需求变更必须区分“修改 / 新增 / 删除”，并在发布影响、验证和回滚中逐项追踪；
> 4. 需求变更不得覆盖旧发布方案，必须在文末只追加历史快照、发布结果和遗留问题；
> 5. 文档未明确的信息，不视为已确认或已完成。

# 发布策略

> 不要求描述平台底层实现，只描述本次发布如何执行。
> 可以选择“灰度”、“滚动”和“灰度+滚动”三种方式。

> 滚动：核心目标是零停机，是最常用策略。滚动发布期间，新旧版本实例同时处理请求.

> 适合场景：
> 改动较小，例如普通 Bug Fix、字段增加、内部重构；
> 新旧版本完全兼容；
> DB / Redis / Kafka / Dubbo 接口没有破坏性变化；
> 服务本身无复杂状态；
> 出问题可以快速回滚；
> 服务已有完善的 readiness、graceful shutdown、监控和告警。

滚动方式下的核心参数：
- 发布方式：滚动
- 最大不可用实例数: 0（多数情况都是0）；
- 最大新增实例数: 1（多数情况都是1）；
- 新实例就绪探测URL：---
- 间隔时长：30s；
- 旧实例退出方式：immediate/graceful

# 回滚方案

> 团队统一回滚到**上一个已发布产物**，不跨版本回滚，也不在本方案中固定指定历史版本号。
>
> 涉及数据库、缓存、消息、配置或任务变更时，必须明确这些状态在应用版本回滚时如何处理。
>
> **回滚不是“把服务版本退回”即结束，必须完成回滚后的业务和技术验证。**

## 触发条件

满足以下任一适用条件，立即停止继续发布或放量，并进入回滚流程。  
可量化的条件必须在发布前填写阈值和持续时间。

- 核心接口错误率超过【阈值】并持续【时间】；
- 核心功能不可用；
- 出现数据错误或状态不一致；
- Kafka Lag 超过【阈值】并持续【时间】；
- MySQL 出现异常锁等待、慢 SQL 或其他发布相关异常，超过【阈值】；
- JVM CPU、内存或 Full GC 超过【阈值】并持续【时间】；
- 本服务提供接口或依赖服务接口调用异常；
- 用户投诉或业务异常明显增加；
- 任一强制检查项未通过；
- 无法在【时间】内判断本次发布是否正常。

> 回滚服务必须结合本次后端服务依赖填写。

## 回滚步骤
1. 停止继续发布或放量；
2. 关闭本次功能开关（如有），并根据本方案暂停相关任务、Producer 或 Consumer；
3. 保留日志、Trace、监控和现场信息；
4. 按“回滚服务”中的决定和顺序处理各后端服务；
5. 恢复需要回滚的 Nacos 配置；
6. 按已确认方案执行数据库回滚或前向修复；
7. 按本方案处理 Redis、Kafka、XXL-JOB 等运行状态；
8. 执行核心技术验证；
9. 执行核心业务验证和数据校验；
10. 观察关键指标恢复到发布前基线；
11. 发布负责人确认回滚完成并同步结果。
