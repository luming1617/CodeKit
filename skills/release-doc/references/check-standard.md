# 质量标准（Quality Standards）

> 用于评审后端发布方案是否完整、可追溯、可执行且满足发布准入要求。发布方案必须以 [release-doc-template.md](release-doc-template.md) 为格式和内容基准；本文档只补充评审标准，不替代模板。

## 适用场景

- 评审由 TDD、技术方案正文或 technical-doc-template.md 提取生成的后端发布方案；
- release-doc Skill 生成后的自检；
- Release Plan Reviewer Sub-agent 或人工独立发布方案评审；不得用代码审查 Skill 代替；
- 发布前确认方案是否具备执行、验证和回滚条件。

## 评审结论

评审结果只能为以下四种之一：

- **通过**：模板结构完整，所有适用信息有来源或证据，所有强制发布前检查具备通过条件，发布、验证、观察和回滚路径可执行。
- **不通过**：存在缺失、矛盾、无证据的通过结论、不可执行步骤、未覆盖的基础设施/依赖变更，或高风险变更错误使用本模板。
- **需人工补充**：文档结构和已提取内容基本完整，但 MR、构建产物、发布系统、监控、负责人或实际环境状态无法由 AI 访问。此结果不等于发布放行；补充后必须重新确认最终状态。
- **请求修改**：存在可以通过修改发布方案解决的缺失、矛盾或不可执行项；修改后必须重新进行独立评审。
- **阻塞**：评审输入缺失、快照不一致、契约无法验证、独立评审不可用，或需要外部事实/权限才能判断；此结果不得作为发布放行。

评审时必须区分“方案尚未执行”和“发布已完成”：

- 发布方案生成阶段，发布步骤、发布后验证、发布后观察、发布结果可以保留模板规定的“待执行”或“【填写】”；
- 发布前检查的最终状态只能使用模板规定的“通过”或“不涉及”，不能用“待确认”“未完成”“无法判断”冒充放行；
- “无法校验”只能出现在发布前检查的 AI 校验结果中，不能作为最终状态或成功结论；
- 发布结果只有在实际执行完成、最终验证为“通过”且所有适用检查项均为“通过”时，才能写为“成功”。

## 总体原则

1. **模板优先**：严格保留模板的章节顺序、标题、表头、状态值、提示语和条件章节。
2. **事实可追溯**：每项发布事实都能追溯到 TDD、项目文件、MR、构建/发布流水线、监控证据或用户明确输入。
3. **不确定性显式化**：未提供或无法访问的信息必须保留为“【填写】”、“【填写/不涉及】”或“需人工补充”，不得猜测。
4. **风险前置**：先识别资金、账务、交易、用户资产、不可逆数据迁移、停机和降级风险，再决定模板和发布策略。
5. **可执行可验证**：每个发布动作都有顺序、执行人、结果和停止条件；每个结论都有验证方式和证据。
6. **回滚闭环**：回滚不仅恢复应用产物，还必须覆盖配置、数据库、Redis、Kafka、XXL-JOB 及业务数据状态。

## 一、来源与事实完整性

- [ ] 明确记录 TDD/技术方案来源的 URL、路径或正文依据。
- [ ] 没有 TDD 时，已读取 technical-doc-template.md，并明确区分模板结构与实际变更事实。
- [ ] 没有把技术方案模板中的示例、“【填写】”、TBD、空字段或设计建议当作已确认信息。
- [ ] 已明确本次发布的业务目的、影响功能、用户影响和预期结果。
- [ ] 已明确本服务边界、实际发布服务、changed module 和服务发布顺序。
- [ ] 服务、repo URL、MR、构建产物、负责人、发布时间、发布时长和监控链接均有来源；无法访问的字段已标记需人工补充。
- [ ] TDD 中缺失的章节没有被直接判定为“无变更”或“不涉及”。
- [ ] 技术方案中的每项实际变更都能在发布方案中找到对应落点，至少覆盖接口、依赖、基础设施、验证或回滚。
- [ ] PRD/TDD 的 `修改 / 新增 / 删除` 台账逐项映射到发布影响、验证和回滚；删除项有清理、兼容或不涉及证据。
- [ ] 需求变更时只追加上一版有效 RPD 快照，并保留既有发布结果、评审处理记录和遗留问题。

## 二、模板结构完整性

- [ ] 文档标题为后端服务发布方案，且没有输出成后端技术方案。
- [ ] 完整保留以下章节，顺序与模板一致：
  关键信息、变更业务、变更服务、变更产物、变更接口、基础设施变更、依赖变更、发布前检查（人工 / AI）、发布策略、发布步骤、发布后验证、发布后观察、回滚方案、发布结果、遗留问题。
- [ ] 基础设施变更、依赖变更、发布后验证、发布后观察、回滚方案、遗留问题没有因“不涉及”而删除。
- [ ] 所有模板表头、必填字段、状态枚举和条件章节均保留，没有用自定义摘要替代。
- [ ] 关键信息已填写需求、文档、工单、负责人、风险等级、发布方式、时间、停机、资金/账务/交易/资产和业务降级字段。
- [ ] Technical Design Document 字段指向实际 TDD 或技术设计来源；没有 TDD 时明确说明资料缺失或使用的模板来源。

## 三、变更服务、产物与接口

- [ ] 变更服务只列实际需要发布的服务，表格顺序就是发布顺序。
- [ ] 每个服务都写清仓库、changed module、MR、主要内容、影响范围和必要的前置依赖。
- [ ] 没有使用“其他服务统一发布”替代多服务的真实发布顺序。
- [ ] 变更产物中每个实际发布服务都有镜像、JAR 或其他生产产物，以及对应构建/流水线来源。
- [ ] 已确认每个服务可以获取并部署上一个已发布产物；没有把源码提交或 MR 当作回滚产物。
- [ ] Maven 发布产物已填写坐标、正式版本、发布状态和仓库/流水线；不涉及时写明原因。
- [ ] 变更接口只描述本服务对外提供的 HTTP、Dubbo 或 WebSocket 变化。
- [ ] 本服务依赖的接口变化已移至依赖变更，并标明依赖方发布前置条件。
- [ ] 新增、修改、删除接口均有兼容性判断和可执行的验证方式；删除接口有调用方影响确认。
- [ ] HTTP、Dubbo、WebSocket 的状态只使用模板允许的“通过 / 不涉及”，且证据与说明完整。

## 四、基础设施与依赖变更

### MySQL

- [ ] 新增/修改表结构 SQL、数据初始化 SQL、发布后校验 SQL 均已列出；无对应变更时明确“不涉及”和原因。
- [ ] 已说明 DDL 执行人、执行时机、锁/性能风险、影响范围和执行结果确认方式。
- [ ] 已检查 nullable/default、索引、唯一约束、金额精度、并发/死锁、慢 SQL 和 EXPLAIN（适用时）。
- [ ] 未使用不可逆的删除/重命名方式破坏新旧版本兼容；无法回滚时已给出前向修复和升级审批路径。
- [ ] 已给出回滚 SQL 或前向修复方案，并说明数据校验方式。

### Redis

- [ ] 每个变更 Key 都有名称、类型、TTL、value 结构、读写方和版本兼容策略。
- [ ] 已说明发布时的清理、预热、重建、保留或失效处理，以及回滚后的缓存状态。
- [ ] 已检查脏数据、旧新结构共存、TTL 和缓存击穿/雪崩风险。

### MQ / Kafka

- [ ] Consumer 已说明 topic、group、起始位置、重试、幂等、DLQ、积压、暂停/恢复和兼容性。
- [ ] Producer 已说明 topic、key、分区、replica、Ack、保留策略、顺序、消息结构和停止生产方式。
- [ ] 已检查新旧消息契约、顺序键、分区/副本、Ack、重试上限和积压处理，不允许无限重试。
- [ ] 消费或生产状态在应用回滚时的处理方式已明确。

### Nacos 与 XXL-JOB

- [ ] Nacos 已说明 Data ID、Group、Namespace、服务、变更内容、生效方式、生效范围和回滚方式。
- [ ] 已确认配置备份、默认值、动态刷新、环境隔离和生效时机。
- [ ] XXL-JOB 已说明 Name、Handler、Cron、执行策略、发布前/后的状态、暂停与恢复方式和回滚处理。
- [ ] 已检查任务幂等、多实例并发、重试和最终开关状态。

### 依赖

- [ ] Maven 依赖变更已列出正式版本，且不存在未处理的 SNAPSHOT。
- [ ] 本服务依赖的 Dubbo、HTTP、WebSocket 接口已标明提供方、兼容性和是否已先发布。
- [ ] 每个依赖变更都有验证证据或明确的人工补充项。

## 五、发布策略与发布步骤

- [ ] 发布方式明确选择 灰度、滚动 或 灰度+滚动，并与风险、兼容性和服务能力匹配。
- [ ] 灰度方案明确分流维度、首批范围、HTTP gateway header routing、Dubbo tag routing、批次比例、观察时长和全链路灰度要求。
- [ ] 滚动方案明确最大不可用实例数、最大新增实例数、readiness URL、间隔时长、旧实例退出方式和副本数要求。
- [ ] 已检查新旧版本的 API、数据库 schema、消息、缓存、配置和依赖兼容性。
- [ ] 已明确异常停止、流量归零、保留灰度实例、停止发布或放量的操作和执行人。
- [ ] 发布步骤只包含后端服务发布操作，且按真实顺序逐步列出执行人和操作结果。
- [ ] MySQL、Redis、MQ/Kafka、Nacos、XXL-JOB 等基础设施在服务发布前完成，并通过发布前检查；没有混入服务发布步骤。
- [ ] 每一步验证失败都有“停止并进入分析/回滚”的分支，不允许默认继续。
- [ ] 多服务方案逐个列出服务和实例发布操作，且顺序与变更服务一致。

## 六、发布前检查、发布后验证与观察

- [ ] 发布前检查（人工 / AI）每行都包含人工结果、AI 结果、最终状态和证据/说明。
- [ ] 最终状态只使用“通过”或“不涉及”；不涉及项写明原因，适用但未完成项不能放行。
- [ ] AI 结论只来自实际可访问的 MR、代码、配置、流水线、发布记录、监控或测试证据；不可访问时写“无法校验”。
- [ ] 已覆盖测试回归、MR 合入、代码范围、接口、MySQL、Redis、MQ/Kafka、Nacos、XXL-JOB、Maven、依赖发布、产物、回滚、告警、负责人、QA 数据与步骤、发布窗口和核心指标。
- [ ] 发布后验证只验证本次变更和受影响链路；技术验证和业务验证都有预期、实际结果、状态和证据。
- [ ] 未涉及的技术或业务验证明确写“不涉及”和原因，不能写“正常”代替验证。
- [ ] 发布后观察已填写发布前基线、通过标准/回滚阈值、灰度后、全量后、观察时长和负责人。
- [ ] 观察指标至少覆盖本次受影响的成功率、P99、资源、错误日志、Kafka Lag（适用时）和核心业务指标。
- [ ] 每个回滚阈值可观测、可判断，并有持续时间或触发条件；不能发布后再补阈值。

## 七、回滚、发布结果与遗留问题

- [ ] 回滚触发条件覆盖错误率、核心功能、数据一致性、Kafka Lag、MySQL 异常、资源指标、依赖接口、用户投诉和强制检查失败等适用风险。
- [ ] 回滚服务已按真实顺序列出是否回滚、回滚方式、执行人和通过标准。
- [ ] 回滚步骤不仅恢复上一个已发布产物，还处理功能开关、Nacos、MySQL、Redis、Kafka、XXL-JOB、Producer/Consumer 和数据修复。
- [ ] 回滚后有应用、配置、数据库、缓存/消息/任务、业务和关键指标验证，并记录证据。
- [ ] 发布结果只由发布负责人在实际发布后填写；成功、回滚、部分回滚和最终验证结论保持一致。
- [ ] 遗留问题保留在文档中；每个遗留问题都有风险、临时措施、负责人和完成时间，没有问题时填写“无”。
- [ ] 高风险变更、不可逆变更或无标准回滚能力没有被标记为 P2/P3 后直接放行。

## 八、禁止的质量问题

以下任一情况都应判定为不通过：

- 缺少 release-doc-template.md 的必需章节、表格或条件章节；
- 把 TDD、PRD 或技术方案大段复制进发布方案，却没有提取发布动作和验证要求；
- 把技术方案模板的占位符、示例或“设计上支持”当作实际发布证据；
- 无证据填写“通过”“正常”“成功”“已发布”或“已回滚”；
- 把“无法校验”“待确认”“未完成”写入发布前检查的最终状态；
- 漏写实际服务、生产产物、基础设施、依赖、发布后观察或回滚后的数据处理；
- 发布顺序与服务清单不一致，或用笼统描述代替真实多服务顺序；
- 发布步骤包含未经发布前检查确认的数据库、缓存、消息、配置或任务操作；
- 回滚只写“重新部署旧版本”，没有处理配置、数据和运行状态；
- 对资金、账务、交易、用户资产、不可逆迁移、删除表/字段等高风险范围使用低风险模板且没有升级审批。
