## 十三、工程结构与设计规范

### 【推荐】应用分层结构：开放 API 层 → Web 层（Controller）→ Service 层 → Manager 层 → DAO 层，上层依赖下层，开放 API 层也可直接依赖 Service 层

- 开放 API 层：封装 Service 接口暴露 RPC / 通过 Web 封装 HTTP / 网关控制层。
- Web 层：访问控制转发、基本参数校验、不复用的简单业务处理。
- Service 层：具体的业务逻辑服务层。
- Manager 层：通用业务处理层——对第三方平台封装（预处理返回、转化异常）、Service 通用能力下沉（缓存方案、中间件通用处理）、多 DAO 组合复用。
- DAO 层：数据访问层，与底层 MySQL、Oracle、Hbase 等交互。

### 【参考】分层领域模型：DO（与数据库表一一对应，DAO 向上传输）、DTO（Service/Manager 对外传输）、BO（Service 层封装业务逻辑）、Query（各层接收查询请求，超过 2 个参数的查询封装禁止用 Map 传输）、VO（Web 向模板渲染层传输）

### 【参考】分层异常处理：DAO 层 catch(Exception e) 后 `throw new DAOException(e)`，不打日志（日志必须在 Manager/Service 层打印）；Service 层异常必须记录到磁盘并尽可能带上参数信息（保护案发现场）；Web 层绝不继续往上抛异常，跳转友好错误页面；开放接口层将异常处理成错误码 + 错误信息返回

### 【强制】二方库 GAV 规则：GroupID 格式 com.{公司/BU}.业务线[.子业务线]（最多 4 级）；ArtifactID 格式 产品线名-模块名；版本号 主版本.次版本.修订号，起始版本必须为 1.0.0（主：不兼容升级；次：兼容性新功能；修订：BUG 修复）

### 【强制】线上应用不要依赖 SNAPSHOT 版本（安全包除外）；依赖二方库群必须定义统一版本变量（如 ${spring.version}）；禁止子项目 pom 中出现相同 GroupId、ArtifactId 但不同 Version 的依赖

### 【强制】二方库新增或升级，保持功能点之外的 jar 包仲裁结果不变；有变化必须明确评估验证（dependency:resolve 前后比对，必要时 dependency:tree 找差异并 <exclude>）

### 【强制】二方库可以定义枚举类型、参数可用枚举，但接口返回值不允许使用枚举类型或包含枚举的 POJO 对象

### 【推荐】所有 pom 依赖声明放 <dependencies>，版本仲裁放 <dependencyManagement>；二方库不要有配置项；谨慎引入不稳定工具包；底层基础框架、核心数据平台、近硬件端系统谨慎引入第三方实现

### 【推荐】服务器调优：高并发调小 TCP time_wait（net.ipv4.tcp_fin_timeout = 30）；调大最大文件句柄数 fd（默认 1024 易出现 open too many files）；JVM 设置 `-XX:+HeapDumpOnOutOfMemoryError`；生产环境 Xms 与 Xmx 设置为相同大小避免 GC 后调整堆的压力

### 【强制】存储方案和底层数据结构的设计必须评审通过并沉淀文档；需求分析中交互 User 超一类且 User Case 超 5 个用用例图；业务对象状态超 3 个用状态图；调用链涉及对象超 3 个用时序图；模型类超 5 个且依赖复杂用类图；2 个以上对象协作且流程复杂用活动图

### 【推荐】类设计符合单一职责原则；谨慎使用继承扩展，优先聚合/组合（不得已用继承须符合里氏代换原则）；依赖倒置（依赖抽象类与接口）；开闭原则（对扩展开放、对修改闭合）；DRY 原则（共性业务抽取公共模块/配置/类/方法，杜绝复制粘贴重复代码）

### 【推荐】架构设计明确：系统边界、模块间依赖关系与宏观输入输出、指导后续设计与演化的原则、非功能性需求（安全性、可用性、可扩展性）；需求分析与系统设计在考虑主干功能时充分评估异常流程与业务边界
