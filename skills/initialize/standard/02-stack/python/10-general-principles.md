## 十、编程建议与总体原则

> 来源：PEP 8（中文版）「引言 / 愚蠢的一致性是狭隘思想的桎梏 / 编程建议」；Google Python 风格指南（中文版）「背景 / 临别赠言」。

### 风格指南的定位与优先级（PEP 8 引言）

PEP 8 提供构成主要 Python 发行版中标准库的 Python 代码的编码约定；本文档和 PEP 257（文档字符串约定）改编自 Guido 最初的 Python 风格指南文章。风格指南会随着时间的推移而演变——新的约定会被识别出来，过去的约定会因语言本身的变化而变得过时。许多项目都有自己的编码风格指南；如果发生任何冲突，此类项目特定的指南在该项目中具有优先权。

### 愚蠢的一致性是狭隘思想的桎梏（PEP 8）

Guido 的一个关键见解是：代码被阅读的频率远高于其被编写的频率，指南旨在提高代码的可读性并使其在广泛的 Python 代码中保持一致——"可读性很重要"（PEP 20）。

风格指南关乎一致性：与本风格指南保持一致很重要；项目内的一致性更重要；一个模块或函数内的一致性最重要。然而，要知道何时可以不一致——有时风格指南的建议并不适用，如有疑问请自行判断、查看其他示例并决定哪种看起来最好，并且不要犹豫提问！特别是：不要仅仅为了遵守本 PEP 而破坏向后兼容性！

忽略特定指南的一些其他充分理由：
- 当应用该指南会使代码的可读性降低时（即使对于习惯阅读遵循本 PEP 的代码的人来说也是如此）。
- 为了与也违反它的周围代码保持一致（可能出于历史原因）——尽管这也是清理别人烂摊子的机会。
- 因为相关代码早于该指南的引入，并且没有其他理由修改该代码。
- 当代码需要与不支持风格指南推荐功能的旧版本 Python 保持兼容时。

编辑代码时，请花几分钟观察一下周边代码的风格：如果这些代码在所有运算符的周围加上了空格，那么你也应该这样做；如果这些代码的注释都用井号形成的框包围起来，那么你的注释也要用井号形成的框包起来（Google《临别赠言》：务必保持一致性）。制定风格指南是为了像字典一样让代码有章可循，让人们可以专注于"写什么"而不是纠结"怎么写"；全局规范就像字典，但是局部的规范同样重要——如果你添加的代码和周围原有的代码大相径庭，就会打乱读者的阅读节奏，不要这样。

### 不要不利于 Python 的其他实现

代码的编写方式不应不利于 Python 的其他实现（PyPy、Jython、IronPython、Cython、Psyco 等）。例如，不要依赖 CPython 在 `a += b` 或 `a = a + b` 形式的语句中高效地实现就地字符串拼接——这种优化即使在 CPython 中也是脆弱的（只适用于某些类型），并且在不使用引用计数的实现中根本不存在。在库中对性能敏感的部分，应改用 `''.join()` 形式，这将确保拼接在各种实现中以线性时间进行。

### 与 None 比较用 is / is not

与 `None` 等单例对象的比较应始终使用 `is` 或 `is not`，绝不能使用相等运算符。另外，注意不要在真正想表达 `if x is not None` 时写成 `if x`——例如在测试默认值为 `None` 的变量或参数是否被设置为其他值时，其他值可能具有在布尔上下文中为 false 的类型（例如容器）。

使用 `is not` 运算符而不是 `not ... is`，虽然两种表达式功能相同，但前者更具可读性且更受推荐：`if foo is not None:` 正确，`if not foo is None:` 错误。

### 富比较与排序

在使用富比较实现排序操作时，最好实现所有六个操作（`__eq__`、`__ne__`、`__lt__`、`__le__`、`__gt__`、`__ge__`），而不是依赖其他代码只执行特定的比较；为减少所需工作，`functools.total_ordering()` 装饰器提供了生成缺失比较方法的工具。PEP 207 指出 Python 假定反射性规则：解释器可以将 `y > x` 交换为 `x < y`、将 `y >= x` 交换为 `x <= y`，并且可以交换 `x == y` 和 `x != y` 的参数；`sort()` 和 `min()` 保证使用 `<` 运算符，`max()` 使用 `>` 运算符。但最好实现所有六个操作，以免在其他上下文中产生混淆。

### 用 def，不要把 lambda 赋值给标识符

始终使用 `def` 语句，而不是将 lambda 表达式直接绑定到标识符的赋值语句：

```python
# 正确:
def f(x): return 2*x

# 错误:
f = lambda x: 2*x
```

第一种形式意味着生成的函数对象的名称是特指的 `f` 而不是通用的 `<lambda>`，这对回溯和一般字符串表示更有用；赋值语句的使用消除了 lambda 表达式相对于显式 def 语句的唯一好处（即它可以嵌入到更大的表达式中）。

### 上下文管理器的调用方式

当资源是代码特定部分的本地资源时，使用 `with` 语句以确保在使用后及时可靠地清理它，`try/finally` 语句也是可以接受的。上下文管理器应通过单独的函数或方法调用，除非它们除了获取和释放资源之外还执行其他操作：

```python
# 正确:
with conn.begin_transaction():
    do_stuff_in_transaction(conn)

# 错误:
with conn:
    do_stuff_in_transaction(conn)
```

后一个示例没有提供任何信息来表明 `__enter__` 和 `__exit__` 方法除了在事务后关闭连接之外还做了其他事情；在这种情况下，明确性很重要。

### return 语句保持一致

在 `return` 语句中保持一致：函数中所有的 `return` 语句要么都返回一个表达式，要么都不返回。如果任何 `return` 语句返回一个表达式，则所有不返回值的 `return` 语句都应明确声明为 `return None`，并且在函数的末尾（如果可达）应存在一个明确的 `return` 语句：

```python
# 正确:
def foo(x):
    if x >= 0:
        return math.sqrt(x)
    else:
        return None

def bar(x):
    if x < 0:
        return None
    return math.sqrt(x)

# 错误:
def foo(x):
    if x >= 0:
        return math.sqrt(x)

def bar(x):
    if x < 0:
        return
    return math.sqrt(x)
```

### 前缀/后缀检查与类型比较

使用 `''.startswith()` 和 `''.endswith()` 而不是字符串切片来检查前缀或后缀——`startswith()` 和 `endswith()` 更清晰、更不容易出错（`if foo.startswith('bar'):` 正确，`if foo[:3] == 'bar':` 错误）。对象类型比较应始终使用 `isinstance()` 而不是直接比较类型（`if isinstance(obj, int):` 正确，`if type(obj) is type(1):` 错误）。

### 序列真值

对于序列（字符串、列表、元组），利用空序列为假的事实：`if not seq:`、`if seq:` 正确；`if len(seq):`、`if not len(seq):` 错误。

### 字符串字面量与布尔比较

不要编写依赖于重要尾随空白符的字符串字面量——这种尾随空白符在视觉上无法区分，一些编辑器（或 reindent.py）会将其修剪。不要使用 `==` 将布尔值与 `True` 或 `False` 进行比较：`if greeting:` 正确，`if greeting == True:` 错误，`if greeting is True:` 更糟糕。

### 工具链（Google 背景）

Python 是谷歌使用的重要动态语言，风格指南列举了 Python 程序应采纳和避免的风格。为帮助正确地格式化代码，谷歌提供了 Vim 配置文件（google/styleguide 仓库中的 `google_python_style.vim`），Emacs 用户保持默认设置即可；许多团队采用 Black 和 Pyink 作为自动格式化工具，以避免格式上的争论。
