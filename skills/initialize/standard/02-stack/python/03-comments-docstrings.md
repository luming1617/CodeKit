## 三、注释与文档字符串

> 来源：Google Python 风格指南（中文版）「注释和文档字符串 (docstring) / 标点符号、拼写和语法 / TODO (待办) 注释」；PEP 8（中文版）「注释」。

### 注释总体要求

与代码相矛盾的注释比没有注释更糟糕；代码更改时，始终将注释保持最新作为优先事项。注释应该是完整的句子，第一个单词应大写（除非它是以小写字母开头的标识符，切勿更改标识符的大小写）。块注释通常由一个或多个完整句子组成的段落构成，每个句子以句点结尾；多句子注释中句末句点后应使用一个或两个空格（最后一个句子除外）。

注释应该和记叙文一样可读，使用恰当的大小写和标点；一般而言完整的句子比残缺句更可读，较短的注释（比如行尾注释）可以更随意，但要保持风格一致。非英语国家的 Python 程序员：请用英语编写注释，除非百分之百确定代码永远不会被不懂该语言的人阅读。

绝不要仅仅描述代码——应该假设读代码的人比你更懂 Python，只是不知道代码要做什么。反例：`# 不好的注释: 现在遍历数组 b, 确保每次 i 出现时, 下一个元素是 i+1`。

### 块注释

块注释通常适用于其后的一些（或所有）代码，并与该代码缩进到同一级别；每一行都以 `#` 和一个空格开头（除非是注释内的缩进文本），段落用只包含 `#` 的行分隔。代码中复杂的部分要写注释：如果以后在代码评审时要解释某段代码，现在就应该加上注释——在复杂操作开始前写上若干行注释。

### 行内注释

少量使用行内注释。行内注释与语句至少相隔两个空格，以 `#` 和一个空格开头（Google：为提高可读性，注释的井号和代码之间应有至少 2 个空格，井号和注释之间至少有一个空格）。说明了显而易见内容的注释是不必要的、甚至分散注意力：`x = x + 1  # Increment x` 不要这样做，但有时有用：`x = x + 1  # Compensate for border`。对于不是一目了然的代码，应在行尾添加注释，如 `if i & (i-1) == 0:  # 如果 i 是 0 或者 2 的整数次幂, 则为真。`

### 文档字符串（docstring）通用规则

文档字符串是包、模块、类或函数里作为第一个语句的字符串，可用对象的 `__doc__` 成员自动提取并为 `pydoc` 所用。编写良好文档字符串的约定永久记录在 PEP 257 中。

- 为所有公共模块、函数、类和方法编写文档字符串；非公共方法不需要，但应有一个描述其功能的注释，出现在 `def` 行之后。
- 结束多行文档字符串的 `"""` 应单独成行；单行文档字符串将结束的 `"""` 保持在同一行：`"""Return an ex-parrot."""`。
- Google：文档字符串一定要用三重双引号 `"""` 格式（依据 PEP-257）；应是一行概述（整行不超过 80 个字符），以句号、问号或感叹号结尾；如写更多注释（推荐），概述后必须紧接一个空行，剩下的内容缩进与文档字符串第一行第一个引号对齐。

### 模块与文件

每个文件应该包含一个许可协议模版，根据项目使用的许可协议（Apache 2.0、BSD、LGPL、GPL 等）选择合适的模版。文件开头应该是文档字符串，描述该模块内容和用法：

```python
"""模块或程序的一行概述, 以句号结尾.

留一个空行. 接下来应该写模块或程序的总体描述. 也可以选择简要描述导出的类和函数,
和/或描述使用示例.

经典的使用示例:

foo = ClassFoo()
bar = foo.FunctionBar()
"""
```

测试模块：测试文件不必包含模块级文档字符串，只有在文档字符串能提供额外信息时才需要写入（例如运行测试所需的特殊要求、不常见的初始化模式、外部环境的依赖）。不要使用不能提供额外信息的文档字符串（如 `"""foo.bar 的测试."""`）。

### 函数和方法的文档字符串

本节中的"函数"指函数、方法、生成器 (generator) 和特性 (property)。满足下列任意特征的任何函数都必须有文档字符串：是公开 API 的一部分；长度过长；逻辑不能一目了然。

文档字符串应提供充分的信息，让调用者无需阅读函数代码就能调用函数；描述函数的调用语法和语义信息，而不描述具体实现细节，除非这些细节会影响函数的用法（比如副作用会修改某个传入的对象，就需要说明）。对于微妙、重要但与调用者无关的实现细节，还是在代码中间加注释更好。

可以是陈述句（`"""Fetches rows from a Bigtable."""`）或祈使句（`"""Fetch rows from a Bigtable."""`），但一个文件内的风格应当一致。对 `@property` 修饰的数据描述符，应采用和属性或函数参数一样的风格（`"""Bigtable 路径."""` 而非 `"""返回 Bigtable 路径."""`）。

覆写基类方法的子类方法可以用简单的文档字符串引导读者阅读基类（如 `"""参见基类."""`），避免到处复制；但如果覆写方法与基类截然不同或有更多细节需要记录（例如有额外的副作用），子类文档字符串至少要描述这些区别。

函数的部分特征应在以下特殊小节中记录。每小节有一行标题，标题以冒号结尾；除标题行外，小节其他部分应有 2 个或 4 个空格（同一文件内保持一致）的悬挂缩进。如果函数名和签名可以见名知意，一行文档字符串就能恰当描述该函数，则可以省略这些小节。

- **Args（参数）**：列出所有参数名，参数名后是冒号、然后一个空格或者换行符，最后是描述。描述超过 80 字符时，应比参数名所在行多 2 个或 4 个空格的悬挂缩进。代码没有类型注解时，描述中应说明所需类型。有形如 `*foo`（可变长参数列表）或 `**bar`（任意关键字参数）的参数时，列举参数名应写成 `*foo` 和 `**bar` 格式。
- **Returns（返回）**：生成器应该用 "Yields:"（生成）。描述返回值的类型和意义；函数仅返回 `None` 时可省略；文档字符串若以 Returns/Yields 开头（如 `"""返回 Bigtable 的行, 类型是字符串构成的元组."""`）且已足以描述返回值，也可省略。不要模仿 Numpy 风格——把返回元组写得像多个有名字的值且没提到返回的是元组；应描述为 "返回: 一个元组 (mat_a, mat_b), 其中 mat_a 是..., 且 ..."。文档字符串中使用的辅助名称不需要和函数体的内部变量名一致（这些名称不是 API 的一部分）。
- **Raises（抛出）**：列出与接口相关的所有异常和异常描述，用类似 Args 小节的格式（异常名+冒号+空格/换行，并添加悬挂缩进）。不要在文档中记录违反 API 使用条件时会抛出的异常（这会让违背 API 时出现的效果成为 API 的一部分，是矛盾的）。

```python
def fetch_smalltable_rows(
    table_handle: smalltable.Table,
    keys: Sequence[bytes | str],
    require_all_keys: bool = False,
) -> Mapping[bytes, tuple[str, ...]]:
    """从 Smalltable 获取数据行.

    从 table_handle 代表的 Table 实例中检索指定键值对应的行. 如果键值是字符串,
    字符串将用 UTF-8 编码.

    参数:
        table_handle: 处于打开状态的 smalltable.Table 实例.
        keys: 一个字符串序列, 代表要获取的行的键值. 字符串将用 UTF-8 编码.
        require_all_keys: 如果为 True, 只返回那些所有键值都有对应数据的
            行.

    返回:
        一个字典, 把键值映射到行数据上. 行数据是字符串构成的元组.

    抛出:
        IOError: 访问 smalltable 时出现错误.
    """
```

### 类的文档字符串

类的定义下方应该有一个描述该类的文档字符串；如果类包含公有属性 (attributes)，应该在 `Attributes`（属性）小节中记录这些属性，格式与函数的 `Args` 小节类似。

```python
class SampleClass(object):
    """这里是类的概述.

    这里是更多信息....
    这里是更多信息....

    属性:
        likes_spam: 布尔值, 表示我们是否喜欢午餐肉.
        eggs: 用整数记录的下蛋的数量.
    """

    def __init__(self, likes_spam = False):
        """用某某某初始化 SampleClass."""
        self.likes_spam = likes_spam
        self.eggs = 0

    def public_method(self):
        """执行某某操作."""
```

类的文档字符串开头应该是一行概述，描述类的实例所代表的事物：`Exception` 的子类应该描述这个异常代表什么，而不是描述抛出异常时的环境；不应有无意义的重复（说这个类是一种类）。正确：`class CheeseShopAddress: """奶酪店的地址."""`、`class OutOfCheeseError(Exception): """没有可用的奶酪."""`；错误：`"""一个描述奶酪店地址的类."""`、`"""在没有可用的奶酪时抛出."""`。

### TODO（待办）注释

在临时、短期和不够完美的代码上添加 TODO 注释。待办注释以全部大写的 `TODO` 开头，紧跟着用括号括起来的上下文标识符（最好是 bug 链接，有时是你的用户名）。最好是诸如 `TODO(https://crbug.com/<bug编号>):` 这样的 bug 链接，因为 bug 有历史追踪和评论，而程序员可能发生变动并忘记上下文。TODO 后面应该解释待办的事情。统一 TODO 的格式是为了方便搜索并查看详情；TODO 不代表注释中提到的人要做出修复问题的保证。所以，当你创建带有用户名的 TODO 时，大部分情况下应该用你自己的用户名。

```python
# TODO(crbug.com/192795): 研究 cpufreq 的优化.
# TODO(你的用户名): 提交一个议题 (issue), 用 '*' 代表重复.
```

如果 TODO 的形式类似于"将来做某事"，请确保其中包含特别具体的日期（"2009年11月前解决"）或者特别具体的事件（"当所有客户端都能处理 XML 响应时, 删除这些代码"），以便于未来的代码维护者理解。
